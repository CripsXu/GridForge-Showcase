# 面试演示提纲

**项目希望解释什么？** 用一笔购买串起一次状态变化。先给面试官看剩余金币和空备战席，买一枚棋子并拖入己方阵地，开战后指出己方的中文名，结算返回，再用同一枚棋子开战。这样可以同时观察购买状态、实例身份和临时战斗对象。

**为什么这样拆模块？** PlayerModel 拥有余额和实例编号，BenchModel 与 BoardModel 分别负责槽位和格子，ShopController 协调一次购买所需的多份状态。优点是余额、占位及状态更新各有明确归属。代价是 ShopController 知道多个模型，交易规则继续增加时需要复查边界。

**什么地方值得用 EventBus？** 一次成功购买同时影响商店卡片、备战 UI 和场景表现。事件让这些观察者只订阅自己关心的数据。相反，卡片需要马上显示“余额不足”时，直接使用购买返回值更容易追踪。这是同步主线程通知，耗时监听仍会阻塞调用方。

**战斗数据与 Actor 为什么分开？** 把胶囊隐藏或销毁不会消除购买记录。上阵时原实例仍归 BoardModel，战斗工厂创建本场 BattleUnit。Presenter 读取位置和死亡状态，ActorManager 管理本场胶囊和头顶名字。战后可以丢弃本场对象并恢复原站位。代价是需要维护两套身份和清理顺序。

**一次攻击怎样发生？** Runner 将帧时间交给 Tick。单位先找目标，超出射程就提交移动；在射程内且冷却结束则提交攻击。决策完成后统一应用移动和伤害，最后检查胜负。这允许同一帧已提交的攻击一起结算。帧步长可变，当前实现没有锁步或回放确定性保证。

**当前局限有哪些？** 敌方阵容固定，近战单位没有绕行、分离或障碍寻路。双方死亡或超时共用 Draw。吉伊有独立模型和动画，其余单位用名称和阵营色区分胶囊；摄像机角度、单位重叠和屏幕尺寸都会影响阅读。EventBus 隐含了通知关系，排查问题仍要回到发布与订阅位置。未做性能基准，不能给出优化收益数字。
